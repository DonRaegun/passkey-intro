# 인증 구현 설명서 (T08 · 패스키)

공개 소개 페이지 안에 **비공개 영역**을 만들고, 비밀번호 없이 WebAuthn 패스키로만 열리게 했습니다. 비공개 영역의 내용은 모두 직접 만들어 넣은 **가상의 내용**이고 실제 개인정보는 없습니다. (공개 영역의 이름·소속·연락처는 1번 과제에서 이어 온 공개 정보입니다.)

## ① 무엇으로 붙였나

- **직접 구현 + 라이브러리 사용.** 챌린지 보관·일회용 처리, 세션, 접근 제어, 패스키 목록·삭제는 직접 짰습니다. 등록·로그인 응답의 서명·공개키 검증은 라이브러리 **`@simplewebauthn/server` 14.1.0**(서버)과 **`@simplewebauthn/browser` 14.0.0**(브라우저)이 합니다.
- 서버: Node.js + Express. 저장소: axhub PostgreSQL(한 행의 JSONB). 로컬에서는 파일(`data.json`).
- 비밀번호 입력 칸은 어디에도 없습니다.

## ② 왜 그걸 골랐나

- 서명 검증은 틀리기 쉽고 틀리면 인증이 뚫리는 부분이라 검증된 라이브러리에 맡기고, 제가 이해하고 설명할 수 있는 부분(챌린지 수명, 세션, 누가 누구 자료를 볼 수 있나)은 직접 구현했습니다.
- 세션 방식(서버 메모리의 랜덤 토큰 + HttpOnly 쿠키)을 고른 이유: 계정이 적고 서버가 한 대라서 가장 단순하고, 로그아웃하면 서버에서 바로 지워 같은 값으로 다시 요청할 수 없습니다. 토큰(JWT)은 로그아웃 즉시 무효화하기 어려워 쓰지 않았습니다.
- 챌린지는 쿠키 `cid`로 서버 메모리의 값과 이어 두고, 한 번 꺼내면 성공·실패와 상관없이 즉시 지웁니다. 그래서 같은 응답을 다시 보내도 통하지 않습니다.
- 패스키가 하나만 남으면 삭제를 막았습니다. 하나도 없으면 로그인할 방법이 없어지기 때문입니다.

## ③ 어디를 어떻게 고쳤나

기존 `index.html`(1번 과제 소개 페이지)에 비공개 영역을 이어 붙이고, 서버를 새로 만들었습니다. (소스는 `server.js` 한 파일과 `public/index.html`)

| 흐름 | 브라우저 (`public/index.html`) | 서버 (`server.js`) |
|---|---|---|
| **등록** | `register()` → `/api/register/options` 요청 → `startRegistration` → `/api/register/verify` | `POST /api/register/options`: 챌린지 발급·보관(`issue`), 공개키 요청 옵션 생성 → `POST /api/register/verify`: 챌린지 꺼내기(`take`) → `verifyRegistrationResponse` → 공개키·자격증명 ID·이름·날짜 저장 → 세션 발급(`login`) |
| **로그인** | `btnLogin.onclick` → `/api/login/options` → `startAuthentication` → `/api/login/verify` | `POST /api/login/options`: 새 챌린지 발급 → `POST /api/login/verify`: 챌린지 꺼내기 → 저장된 공개키로 `verifyAuthenticationResponse` → 성공해야 세션 발급 |
| **로그아웃** | `btnLogout.onclick` → `POST /api/logout` | `POST /api/logout`: `sessions.delete(sid)`, 쿠키 삭제 |
| **비공개 자료 조회** | `refresh()` → `GET /api/private`, `GET /api/passkeys` | `requireAuth`(세션이 없으면 **401**) → `GET /api/private`는 세션 계정의 자료만 반환. `GET /api/users/:name/private`는 이름이 내 계정이 아니면 **403** |

- 거절을 만드는 소스 위치: 로그인 없음 401 → `server.js`의 `requireAuth`, 남의 자료 403 → `GET /api/users/:name/private`, 이미 쓴 챌린지 → `take()`, 서명 위조 → `verifyAuthenticationResponse` 예외 처리.
- 비공개 자료는 로그인한 뒤에만 서버에서 받아 화면에 그립니다. 공개 HTML과 스크립트에는 비공개 내용이 들어 있지 않습니다.
- 안드로이드 일부 브라우저가 요청 출처를 `android:apk-key-hash:…`로 보내서 등록이 막힌 적이 있어, 이 형식(43자)만 추가로 허용하도록 `origins()`를 고쳤습니다.

## ④ 안 열리는 것을 확인한 기록

확인은 두 가지로 했습니다. **(가)** 소프트웨어 인증기(`test/verify.js`, 18개 항목)로 서버 로직을 전부 자동 확인했고 기록이 `test/evidence.txt`입니다. **(나)** 실제 폰 패스키로 배포 주소에서 등록·로그인하고 아래 `접근 차단 확인` 칸으로 확인했습니다. (실제 기기 캡처는 제출 전에 채웁니다.)

### 1. 로그인 없이 열기
- 거절: `GET /api/private` → **401** `{"error":"패스키 로그인이 필요합니다"}`
- 통과: 패스키 로그인 후 `GET /api/private` → 200, 자료 6건(계정A)
- 로그인 전에 받은 페이지 소스에는 `가상기업`·`시간대별 강수` 같은 비공개 문구가 없습니다.

### 2. 남의 패스키로 열기 (계정 두 개)
- 거절: 계정A로 로그인해 `GET /api/users/계정B/private` → **403** `{"error":"다른 계정의 자료입니다"}`
- 거절: 반대로 계정B로 `GET /api/users/계정A/private` → **403**
- 건수: 거절 전후로 A 6건·B 7건 그대로.
- 통과: 쿼리에 `?account=계정B`를 적어도 → **200** 이지만 `owner`는 계정A, 계정A 자료만 돌아옵니다.

### 3. 사용한 챌린지 재사용
- 통과: 새 챌린지로 서명해 `POST /api/login/verify` → **200**
- 거절: 같은 응답을 한 번 더 제출 → **400** `{"error":"챌린지가 없거나 이미 사용되었습니다"}`
- 거절: 챌린지는 맞지만 서명이 다른 내용에 대한 것(위조) → **401** `{"error":"서명 검증 실패: 서명 불일치"}`
- 로그인·등록 요청마다 챌린지 값은 매번 다릅니다(기록의 앞 12자: `nnltGpzRZV…` ≠ `gF9WbJasbv…`).

### 4. 패스키 삭제 뒤 로그인
- 통과: 패스키 두 개 중 하나를 지운 뒤 **남은 패스키**로 로그인 → **200**
- 거절: **지운 패스키**로 로그인 → **401** `{"error":"등록되지 않았거나 삭제된 패스키입니다"}`
- 마지막 하나 삭제 → **409** `{"error":"마지막 패스키는 지울 수 없습니다 (지우면 로그인할 방법이 없어집니다)"}`. 화면에도 같은 안내가 있습니다.

### 로그아웃 뒤 같은 값으로 다시 요청
- 거절: 로그아웃 전에 쓰던 세션 값으로 `GET /api/private` → **401**
- 세션·서명 값은 기록에서 `***가려짐***`으로 처리했습니다.

## ⑤ AI와 나

- **AI에게 맡긴 일:** 서버 코드(챌린지 보관·세션·접근 제어)와 화면, 소프트웨어 인증기 테스트 스크립트, axhub 배포 설정, 설명서·제출문 초안, 공개 페이지 디자인 초안.
- **내가 직접 판단한 일:** 배포처를 axhub로 정했고, 1번 과제 페이지에 이어 붙이되 저장소 이름과 주소를 직접 바꿨습니다. 학원 PC에 개인정보가 남지 않도록 패스키를 폰으로 만들기로 했고, 공개 페이지에 올릴 프로젝트를 직접 골랐습니다(다이어리·패스키 카드는 빼고 카지노는 넣음, 비공개 저장소의 JARVIS는 링크 없이 "개발 중"으로 표기).
- **AI 제안을 따르지 않은 일:** 디자인 초안이 "밤티"라고 보고 두 번 다시 만들게 했고, AI가 두는 쪽을 권한 "만들면서 내린 판단" 섹션은 필요 없다고 지웠습니다. JARVIS는 데모 녹화를 기다리자는 제안 대신 "개발 중"이라고만 적기로 했습니다.

## ⑥ 아직 못 막은 것

- **로그인 시도 횟수 제한이 없습니다.** 누가 `/api/login/verify`에 계속 요청해도 막지 않습니다. 서명을 위조할 수는 없지만 서버에 부하를 줄 수 있습니다. (속도 제한 미들웨어를 붙일 예정)
- **세션과 챌린지가 서버 메모리에 있습니다.** 서버를 다시 켜면 모두 로그아웃되고, 서버를 둘 이상 띄우면 챌린지를 못 찾습니다.
- **안드로이드 출처는 형식만 확인합니다.** `android:apk-key-hash:` 뒤 43자 형식이면 어떤 앱이든 받습니다. 허용할 앱 해시를 고정 목록으로 좁혀야 합니다.
- **계정 만들기에 제한이 없습니다.** 누구나 새 계정 이름으로 계정을 만들 수 있고, 지우는 기능이 없습니다.
- 모든 계정 데이터는 한 행(JSONB)에 덮어쓰기 때문에, 동시에 두 요청이 저장하면 한쪽이 사라질 수 있습니다.
- 실제 기기 검증은 폰 한 대와 소프트웨어 인증기로만 했습니다. 하드웨어 보안 키로는 시험하지 않았습니다.

## 짧은 확인 방법

1. **어디로 가나요:** https://gsg-passkey-intro-1gvp.axhub.app 을 새 시크릿 창에서 엽니다. 첫 화면은 공개 소개 페이지이고 계정 없이 열립니다.
2. **세 단계 안에 무엇을 하나요:** ① 맨 아래 노란 띠 아래 "개인 자료 보관함"에서 계정 이름과 패스키 이름을 쓰고 "새 계정 만들고 패스키 등록"을 누른 뒤 기기 확인을 합니다. ② 자료 6~7건이 보이면 로그아웃합니다. ③ 주소창에 `/api/private`를 열어 봅니다.
3. **무엇이 보이면 통과인가요:** 로그인 상태에서는 가상 자료가 보이고, 로그아웃 뒤 `/api/private`는 401 `패스키 로그인이 필요합니다`가 보입니다.
4. **안 될 때는 무엇이 보이나요:** 등록을 취소하면 "등록을 취소했습니다. 서버에는 아무것도 저장되지 않았습니다.", 이미 있는 계정 이름이면 409 안내, 삭제한 패스키로는 "등록되지 않았거나 삭제된 패스키입니다".
