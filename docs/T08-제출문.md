## 재현·통과 확인 4가지
```
어디로 가나요: 결과물 URL(https://gsg-passkey-intro-1gvp.axhub.app/)을 새 시크릿 창에서 엽니다. 첫 화면은 공개 소개 페이지이고 계정 없이 열립니다.
무엇을 하나요(3단계 이내): 1) 주소창에 /api/private를 직접 엽니다. 2) 맨 아래 "개인 자료 보관함"에서 계정 이름을 쓰고 "새 계정 만들고 패스키 등록"으로 패스키를 만든 뒤 가상 자료를 확인합니다. 3) "로그아웃" 후 다시 /api/private를 엽니다.
무엇이 보이면 통과: 1)과 3)은 401 {"error":"패스키 로그인이 필요합니다"}, 2)는 [가상] 표시가 붙은 자료 6~7건이 보이고 "내 패스키"에 이름과 등록 날짜가 보입니다. 로그인 후 "접근 차단 확인" 칸에 다른 계정 이름을 넣으면 403 {"error":"다른 계정의 자료입니다"}가 보이고 내 자료 건수는 그대로입니다.
안 될 때: 등록을 취소하면 "등록을 취소했습니다. 서버에는 아무것도 저장되지 않았습니다.", 이미 있는 계정 이름은 409 안내, 삭제한 패스키로 로그인하면 "등록되지 않았거나 삭제된 패스키입니다", 마지막 패스키를 지우려 하면 "마지막 패스키는 지울 수 없습니다"가 보입니다. 패스키 만들기가 안 되는 PC(Windows Hello 미설정)에서는 폰에서 여세요.
```

## 사실 기록 (제출문 본문에 붙임)

### 서버에 저장되는 값 (C21·C22)
```
서버에 저장되는 것: 자격증명 ID, 공개키(base64url), 서명 횟수 카운터, 패스키 이름, 등록 날짜, 계정 이름.
이 값은 공개키이고 비밀번호가 아닙니다. 공개키로는 서명을 확인할 수만 있고 서명을 만들 수 없습니다. 개인키는 기기(휴대폰·보안 키·Windows Hello) 안에만 있고 서버로 전송되지 않습니다. 비밀번호를 받거나 저장하는 칸이 없습니다.
```

### 개인키가 전송되지 않는 근거 (C23)
```
등록 요청 본문(POST /api/register/verify): { "response": { "id": ..., "rawId": ..., "type": "public-key", "response": { "clientDataJSON": ..., "attestationObject": ... (공개키가 들어 있음), "transports": [...] } }, "name": "패스키 이름" }
이 본문에는 개인키 필드가 없습니다. 기록: test/evidence.txt의 "POST /api/register/verify body=" 줄(값은 ***가려짐*** 처리). 소프트웨어 인증기의 개인키는 인증기 객체 안에만 있고 서버로 나가는 코드가 없습니다.
```

### 챌린지 (C19·C20·C27·C28)
```
서버는 등록·로그인 요청마다 새 챌린지를 만들어 서버 메모리에 보관하고(쿠키 cid로 연결), 검증할 때 꺼내면서 바로 지웁니다.
등록 요청마다 값이 다름: nnltGpzRZV… ≠ gF9WbJasbv… (test/evidence.txt)
로그인 요청마다 값이 다름: 같은 기록의 "로그인 챌린지도 매번 다름" 확인 줄
```

### 로그인 성공과 실패 (C29·C30·C31)
```
성공: 저장된 공개키로 서명 확인 → 200
실패: 서명이 다른 내용에 대한 것(위조) → 401 {"error":"서명 검증 실패: 서명 불일치"}
이미 쓴 챌린지로 같은 응답을 다시 제출 → 400 {"error":"챌린지가 없거나 이미 사용되었습니다"}
```

### 로그인 후 사용자 식별 방식 (C32)
```
세션 방식입니다. 로그인에 성공하면 서버가 랜덤 토큰(32바이트)을 만들어 서버 메모리의 sessions에 계정과 함께 저장하고, 쿠키 sid(HttpOnly, SameSite=Strict, https에서는 Secure)로 내려 줍니다. 로그아웃하면 서버에서 지웁니다.
```

### 로그아웃 뒤 같은 값으로 요청 (C33·C34)
```
로그아웃 전에 쓰던 세션 값(***가려짐***)으로 GET /api/private → 401 {"error":"패스키 로그인이 필요합니다"}
세션·서명 값은 모든 기록에서 가렸습니다.
```

### 패스키가 하나도 안 남으면 (C46)
```
마지막 패스키는 삭제할 수 없습니다(409, "마지막 패스키는 지울 수 없습니다 (지우면 로그인할 방법이 없어집니다)"). 화면에도 같은 안내가 있습니다. 하지만 패스키를 저장한 기기를 잃어버리면 그 계정으로는 들어갈 수 없고 복구 수단이 없습니다. 그래서 패스키를 두 개 이상, 서로 다른 저장소에 등록하도록 했습니다.
```

### 패스키를 저장한 곳 (C26)
```
첫 번째·두 번째 계정(ghs, gong)의 첫 패스키: 휴대폰의 Samsung Pass (삼성 인터넷으로 등록했고, 로그인 때 "Samsung Pass — 로그인에 사용할 패스키 선택" 창에 gong·ghs 두 개가 보임). 학원 PC에 개인정보를 남기지 않으려고 폰으로 등록했습니다.
두 번째 패스키: 구글 비밀번호 관리자 (폰의 크롬으로 등록, 등록 창에 "Google 비밀번호 관리자"로 표시). 첫 패스키(Samsung Pass)와 다른 저장소입니다.
확인한 계정: 삭제·두 줄 목록·마지막 삭제 거절 화면은 시험 계정 wendy(첫 패스키 kakao는 Samsung Pass, 두 번째 google은 구글 비밀번호 관리자)로 찍었습니다. 같은 폰에서 두 번째를 만들 수 있도록 추가 등록 때 "이미 등록된 패스키 제외" 요청은 보내지 않습니다. 같은 저장소에 다시 만들면 기존 패스키가 덮어써질 수 있어 저장소를 다르게 골랐습니다.
```

### 가상 내용 표시 (C12)
```
비공개 영역의 자료는 모두 제가 지어낸 가상의 내용이고 실제 개인정보(연락처·신분증 번호 등)는 없습니다. 각 항목에 [가상] 표시를 붙였습니다. 공개 영역의 이름·소속·이메일은 1번 과제에서 이어 온 공개 정보입니다.
```

### 두 계정과 차단 (C36~C41)
```
계정 두 개(ghs, gong)에 서로 다른 가상 자료가 들어 있습니다(6건·7건).
A→B 요청: GET /api/users/<B>/private → 403 / B→A 요청도 403 (기록: 접근 차단 확인 캡처, test/evidence.txt 5번 항목)
거절 앞뒤로 반대편 자료 건수 동일: A 6건, B 7건
주소나 쿼리에 다른 계정을 적어도: GET /api/private?account=<B>&owner=<B> → 200, owner는 내 계정, 내 자료만 반환
위 거절을 만드는 소스: server.js의 requireAuth(401)와 GET /api/users/:name/private(403)
```

## AI와 내 판단 3줄 (초안 — 사실과 다르면 직접 고치세요)
```
AI에게 맡긴 일: 서버 코드(챌린지 보관·세션·접근 제어)와 화면, 소프트웨어 인증기로 등록·로그인·차단을 확인하는 테스트 스크립트와 기록, axhub 배포 설정, 설명서·제출문 초안, 공개 페이지 디자인 초안.
내가 직접 판단한 일: 배포처를 axhub로 정했고, 1번 과제 저장소의 이름과 주소를 직접 바꿨다. 학원 PC에 개인정보가 남지 않도록 패스키를 폰으로 만들기로 했고, 공개 페이지에 올릴 프로젝트를 직접 골랐다(다이어리·패스키 카드는 뺐고 카지노는 넣었으며, 비공개 저장소인 JARVIS는 링크 없이 "개발 중"으로만 표기).
AI 제안을 따르지 않은 일: 디자인 초안이 마음에 들지 않아 두 번 다시 만들게 했고, AI가 두는 쪽을 권한 "만들면서 내린 판단" 섹션은 필요 없다고 지웠다. JARVIS는 데모 녹화를 기다리자는 제안 대신 "개발 중"이라고만 적기로 했다.
```
